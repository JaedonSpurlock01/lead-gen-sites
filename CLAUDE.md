# lead-gen-sites

Many local lead-gen sites (rank-and-rent service businesses) grouped by niche. One Astro engine per niche, one Cloudflare Worker per site, one Tracer backend for every lead. Expect 100–300 sites; every rule below exists so one person can update one site, one niche, or all of them from here.

## Layers

Sites hold data. Niches hold templates and prompts. Packages hold behavior.

- `niches/<niche>/sites/<id>/`: `site.json`, content, `assets/`, `keyword-map.md`. No code. Content is either `content/services/*.md` (asphalt) or block pages, `content/pages/*.yaml` and `content/services/*.yaml` (dumpster, solar), whose block types are defined in `packages/schema/src/blocks.ts`. `wrangler.jsonc` here is generated by `pnpm build` and gitignored; edit `site.json` instead.
- `niches/<niche>/`: `niche.json` (services, image slots, market fields, theme, layouts, lead form fields, block types it renders), `pages/`, `components/`, `copy/` (shared copy with `{{tokens}}`), `prompts/`. Each niche has its own design. Copy `niches/_template` to start a niche.
- `packages/schema`: zod schemas for every JSON, YAML and Markdown file, the content parser, token substitution, and the site-vs-niche cross checks. A file shape is defined here and nowhere else.
- `packages/engine`: the Astro integration every niche uses (virtual modules, per-site outDir, BaseHead, JSON-LD, sitemap, robots, the injected `/api/lead` route).
- `packages/ui`: shared components themed through CSS variables.
- `packages/leads`: the only `/api/lead` implementation. It validates against the niche's `form` in niche.json.
- `packages/cli`: `new-site`, `check`, `build`, `deploy`, `domains`, `secrets`.
- `config/`: global non-secret settings (Tracer URL per environment, Cloudflare compat/Secrets Store/budgets, zone settings, email DNS).

Placement test: would a roofing niche use it unchanged? Then it belongs in `packages/`. Otherwise it belongs in the niche.

## Rules

- `site.json.domain` is the only source of the hostname: apex, lowercase, no scheme, no `www.`. The business URL, canonical links and the Worker custom domain derive from it.
- `cloudflareProject` is the Worker name. It stays stable for the life of a site; renaming it orphans the live Worker.
- `TRACER_FORM_KEY` reaches Workers through the Secrets Store binding (`await env.TRACER_FORM_KEY.get()`). `TRACER_FORMS_URL` comes from `config/environments.json`. Secrets live only in `.dev.vars` or env vars; a key or token in a tracked file is a bug.
- Sibling sites link one way: if A links to B, B never links to A. `pnpm check` warns past the sibling-link budget in `config/cloudflare.json`.
- Commands that would write to Cloudflare or Tracer (`deploy`, `domains provision`, `secrets rotate`) default to dry-run. The owner runs real cutovers; an agent never deploys, buys domains, creates zones, changes DNS, sets secrets, or attaches domains.
- Verify Cloudflare config keys, limits, rate limits and API endpoints against current Cloudflare docs before relying on them (the Cloudflare docs MCP tool is available).
- Code style matches the asphalt source: double quotes, semicolons, trailing commas, 2-space indent, TypeScript strict, zod for every schema, Vitest with mocked Cloudflare and Tracer.

## Verify

`pnpm check`, `pnpm test`, `pnpm typecheck`. `pnpm build <site>` writes `dist/<site>/`. `pnpm verify-local <site>` runs the site under `wrangler dev` against a mock Tracer.

New sites go through the `new-site` skill (`.claude/skills/new-site/`). CI decides what to deploy with `pnpm affected` (`packages/cli/src/affected.ts`); change the path rules there, not in the workflows.
